# ZCode 分阶段执行方案

> 状态：执行框架 v1  
> 创建时间：2026-08-19（Asia/Shanghai）  
> 适用前提：ZCode 能读取并修改当前工作区，且会遵守根目录 `AGENTS.md`。本文不依赖或假设 ZCode 的专有命令。

## 一、执行目标

用可验证、可审查、可回滚的方式，把 PRD、技术规范和视觉方案逐步转化为一个可以演示、测试和验收的 MVP。先完成一条最小端到端用户闭环，再扩展次要功能。

当前事实：工作区尚未包含三类源资料，也没有产品代码。Phase 0 未通过前，ZCode 不得初始化技术栈或实现业务功能。

## 二、ZCode 全程执行协议

每次只执行一个 Phase，不跨阶段合并。每次开始前必须：

1. 阅读根目录 `AGENTS.md` 和 `tasks/` 下全部任务文档。
2. 检查当前文件、任务状态和上阶段验收证据。
3. 明确本阶段允许修改的范围；保留用户已有修改。
4. 缺少必要输入时停止实现，把问题写入 `tasks/question.md`，不得自行补写需求。

每次结束前必须：

1. 运行与风险匹配的检查或测试，并检查实际输出。
2. 更新 `tasks/todo.md`、`tasks/next-todo.md`、`tasks/communicating.md`；有新风险或未知项时更新 `tasks/advice.md` 和 `tasks/question.md`。
3. 汇报修改文件、验证结果、失败事实、剩余风险和下一阶段进入条件。
4. 不自动部署、不发送外部消息、不写第三方系统、不安装全局软件；这些操作需要用户单独授权。

## 三、阶段总览

| Phase | 目标 | 主要产物 | 进入下一阶段的门禁 |
| --- | --- | --- | --- |
| 0 | 建立资料基线 | 来源登记、版本清单、冲突清单 | 三类源资料可读取且版本明确 |
| 1 | 收敛产品目标与 MVP | 一页实施基线、追踪矩阵、非目标 | 核心场景、成功指标、裁决人明确 |
| 2 | 固化系统边界与契约 | 架构图、调用链、接口/数据契约、风险验证 | 主链路无未解决的 P0 架构问题 |
| 3 | 建立工程基线 | 可启动工程、配置样例、检查与测试入口 | 新环境可按文档复现启动与检查 |
| 4 | 建立视觉与前端骨架 | design tokens、组件状态、页面壳层 | 核心页面结构与视觉基线可核对 |
| 5 | 实现第一条垂直切片 | 端到端 MVP 主流程 | 主成功路径和关键失败路径可演示、可测试 |
| 6 | 补齐质量与异常能力 | 测试、降级、日志、安全与性能证据 | 验收矩阵无阻塞缺口 |
| 7 | 验收与交付准备 | 构建产物、验收报告、发布/回滚清单 | 用户批准后才可进入真实发布 |
| 8 | 试运行与迭代 | 真实反馈、指标、下一版 backlog | 用证据决定扩展、调整或停止 |

## Phase 0：资料接入与基线登记

### 目标

让后续所有需求、架构、视觉和任务结论都能回溯到具体来源。

### ZCode 任务

- 定位 PRD、技术规范、视觉方案，记录路径、标题、版本/日期、负责人和可读性。
- 提取目录和关键主题，不写业务代码。
- 标出版本冲突、缺失章节、术语歧义和无法读取的附件。
- 更新 Q-001、Q-004 和 T-001。

### 交付物与验收

- `tasks/advice.md` 中存在源资料登记表。
- 三类资料都有唯一当前基线；如果没有，`tasks/question.md` 中有明确阻塞问题。
- 验收门：T-001 完成，否则停止。

### 复制给 ZCode

```text
执行 Phase 0。先阅读 AGENTS.md 与 tasks/ 下全部文档。只读检查并登记 PRD、技术规范、前端视觉方案的路径、版本或日期、负责人和可读性；识别冲突与缺失。不要初始化项目、安装依赖或写业务代码。更新 question、todo、next-todo、communicating、advice，并给出 T-001 是否可以完成的证据。
```

## Phase 1：目标收敛、MVP 与追踪矩阵

### 目标

回答“为谁解决什么问题、第一版验证什么、怎样算成功”。

### ZCode 任务

- 提取目标用户、核心场景、痛点、业务成功指标和明确非目标。
- 选择一条最小端到端用户闭环，描述输入、处理、输出和失败路径。
- 建立“需求 → 技术模块 → 视觉状态 → 任务 → 验收证据”追踪矩阵。
- 把冲突放入 `question.md`，不要替用户做产品裁决。

### 交付物与验收

- 一页实施基线：用户、场景、指标、MVP、非目标、边界。
- 追踪矩阵：核心需求不存在无实现、无视觉状态或无验收方式的孤立项。
- 验收门：T-002、T-004、T-006 完成；P0 决策已关闭。

### 复制给 ZCode

```text
执行 Phase 1。仅基于已登记的三类源资料，生成一页实施基线和需求追踪矩阵。确定一个 MVP 垂直闭环及非目标，不新增源资料中不存在的功能。冲突写入 question.md，并暂停相关实现。更新任务状态和 communicating.md，说明每项结论的来源及仍未验证的假设。
```

## Phase 2：架构边界、调用链与契约

### 目标

在写大量代码前固定职责边界，优先验证最危险的技术假设。

### ZCode 任务

- 恢复或设计运行入口、模块职责、主调用链、数据流、配置和测试地图。
- 定义前端、后端/Agent、模型或外部服务、数据存储之间的接口契约。
- 明确鉴权、隐私、超时、重试、幂等、降级、日志和成本边界。
- 对高风险假设做最小技术验证；验证代码必须与生产实现隔离并可删除。

### 交付物与验收

- 架构和调用链说明、接口/数据契约、关键决策记录。
- 风险验证结果明确区分“代码推断”“本地验证”“真实环境证据”。
- 验收门：主链路没有阻塞性的未知接口或数据归属。

### 复制给 ZCode

```text
执行 Phase 2。根据技术规范和已确认 MVP，给出运行入口、模块边界、主调用链、数据流、接口/数据契约、错误与降级策略。优先做最小技术风险验证，不实现完整产品功能。所有未验证结论明确标注证据层级；P0 架构问题未关闭时停止进入 Phase 3。
```

## Phase 3：工程基线

### 目标

建立可重复运行、可检查、可测试、可观测的最小工程。

### ZCode 任务

- 严格沿用技术规范指定的技术栈和依赖管理方式；未指定时先提问。
- 建立最小目录、启动入口、环境变量示例、格式化/静态检查、定向测试和日志入口。
- 不添加 MVP 主链路之外的生产依赖或基础设施。
- 写清本地启动、检查和测试命令。

### 交付物与验收

- 新环境可以依据文档完成安装、启动和最小检查。
- 配置中没有密钥；失败启动能给出可诊断错误。
- 验收门：T-007 完成，实际命令和输出已记录。

### 复制给 ZCode

```text
执行 Phase 3。严格按技术规范建立最小工程基线：目录、运行入口、配置样例、静态检查、定向测试、日志和错误处理。不要实现完整业务，不新增未经批准的生产依赖。实际运行最小启动与检查，并记录命令、输出、失败事实和未覆盖风险。
```

## Phase 4：视觉系统与前端骨架

### 目标

把视觉方案转化为可复用规则和可核对的页面结构，不提前接入复杂业务。

### ZCode 任务

- 提取 design tokens、布局、字体、颜色、间距、圆角、断点和交互规则。
- 建立核心组件和正常、加载、空、错误、禁用状态。
- 完成 MVP 页面壳层与导航；使用固定的非敏感测试数据。
- 做静态检查和必要的浏览器/截图核对，注明其不是完整运行或用户验收证据。

### 交付物与验收

- 页面结构与视觉方案可逐项对照；没有以猜测补齐的关键状态。
- 响应式与可访问性最低要求有检查结果。
- 验收门：视觉差异已记录并由负责人确认或进入问题清单。

### 复制给 ZCode

```text
执行 Phase 4。只依据已确认视觉方案实现 design tokens、核心组件状态和 MVP 页面壳层，使用固定测试数据，不接入完整业务。验证正常、加载、空、错误、禁用和响应式状态。列出视觉差异及证据边界，更新任务记录。
```

## Phase 5：第一条端到端垂直切片

### 目标

用最少代码打通真实主链路，尽早验证产品和系统的关键假设。

### ZCode 任务

- 只实现 Phase 1 确定的 MVP 主闭环。
- 按已确认契约连接前端、接口/Agent、模型或外部服务、数据层。
- 先加入定向测试或最小复现，再实现主成功路径和关键失败路径。
- 对外部服务使用明确的测试替身；不得把 mock 结果当作真实集成证据。

### 交付物与验收

- 一个用户场景可从输入走到可见输出，并能处理至少一个关键失败场景。
- 关键链路有结构化日志和可重复测试。
- 验收门：T-008 完成；演示、测试和证据来源一致。

### 复制给 ZCode

```text
执行 Phase 5。只实现已确认的第一条 MVP 垂直切片，贯通前端、接口或 Agent、外部模型/服务和数据层。先建立定向测试或最小复现，再实现成功路径和关键失败路径。不要扩展次要功能；mock、本地运行、真实集成和部署证据必须分开汇报。
```

## Phase 6：质量、异常、安全与可观测性

### 目标

让 MVP 能运行，也能诊断故障、执行降级并接受验收。

### ZCode 任务

- 补齐空数据、错误、超时、重试、限流、权限不足、外部服务不可用和成本超限路径。
- 增加相关单元、集成和必要端到端测试；检查真实业务输出，不只看退出码。
- 检查敏感数据、日志脱敏、输入边界、依赖风险、性能和基本可访问性。
- 更新追踪矩阵中的验证证据。

### 交付物与验收

- T-009 完成；核心需求有相应测试或人工验收步骤。
- 所有阻塞缺陷有明确状态，未解决风险有负责人和处置计划。

### 复制给 ZCode

```text
执行 Phase 6。围绕 MVP 主链路补齐异常、降级、安全、日志、性能和可访问性检查，并增加风险相称的测试。检查实际业务输出，不把命令退出码 0 等同于业务正确。将证据回填追踪矩阵，列出仍需真实环境或人工验证的项目。
```

## Phase 7：验收与交付准备

### 目标

形成可审查的候选版本，但不自动发布。

### ZCode 任务

- 运行相关测试、类型检查、构建和必要端到端验证。
- 按追踪矩阵逐条核对需求、视觉、技术约束与验收证据。
- 整理运行说明、已知限制、监控指标、发布步骤和回滚条件。
- 检查变更范围，不夹带凭据、缓存、临时文件或无关修改。

### 交付物与验收

- T-010 完成；候选构建产物与验收报告可复现。
- 真实部署、第三方写入或生产变更必须等待用户明确授权。

### 复制给 ZCode

```text
执行 Phase 7。完成候选版本的测试、类型检查、构建和必要端到端验证，逐条回填需求追踪矩阵。整理运行、限制、监控、发布和回滚清单。不要部署或改变任何外部系统；完成后等待用户验收与发布授权。
```

## Phase 8：试运行与迭代

### 目标

用真实用户和运行数据决定下一步，而不是默认继续扩功能。

### ZCode 任务

- 仅在用户授权并具备环境后协助试运行。
- 记录成功率、失败类型、耗时、模型/外部服务成本和用户反馈。
- 将问题区分为需求错误、体验问题、实现缺陷、模型不确定性和环境问题。
- 根据证据更新下一版 backlog，保留停止或缩小范围的选项。

### 复制给 ZCode

```text
执行 Phase 8 的只读分析部分。基于已授权的真实试运行证据，归类成功、失败、性能、成本和用户反馈，更新 backlog 和建议。不要自动部署、发消息或修改第三方系统；涉及外部状态的动作逐项等待用户授权。
```

## 四、推荐的人工检查点

- Phase 0 后：用户确认资料版本与冲突裁决人。
- Phase 1 后：用户确认 MVP、成功指标和非目标。
- Phase 2 后：用户确认架构边界与外部依赖。
- Phase 4 后：用户确认视觉偏差与交互状态。
- Phase 5 后：用户实际演示主流程，再决定是否扩展。
- Phase 7 后：用户决定是否部署或进入试运行。
